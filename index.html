01

Alfie

AI-powered review operations — turning incoming customer reviews into validated, context-aware responses and business actions.

$2M ARR AI-powered product impact

The problem. Restaurants receive reviews continuously across Google, Yelp, Zomato and other platforms. Responding well means understanding the review, the brand, the location, available offers or loyalty actions, business rules, language, and what should happen next. Doing that manually does not scale.

What I built. I led the architecture and end-to-end development of Alfie, a production AI workflow that turns each incoming review into a response-ready business event. Reviews are pulled from multiple platforms through scheduled jobs, normalized, and placed onto a message queue for asynchronous processing.

Each consumer retrieves the appropriate brand context from cache. This context includes the information needed to make the response relevant to that brand, including offers, loyalty actions, business rules, calculations and other operational context.

When a review arrives in another language, Alfie can invoke a translation tool before passing the enriched review and context into the AI workflow. The foundation model generates the candidate response, but the model is not the final authority.

The generated response goes through a deep validation and guardrail layer before it can continue. This allows the AI to operate inside a controlled software system rather than simply generating free-form text.

Once validated, the response is ready for the customer's chosen workflow: it can be automated, or it can be presented to an operator who can review, edit and send it manually.

AI E2E Test Engineering

Verification for software increasingly written by AI.

Requirement → executable test AI-assisted verification workflow

As AI makes it dramatically easier to generate application code, verification becomes an increasingly important engineering step. Writing a test is not enough: the system needs to understand the requirement, the codebase, the application and the state required to actually execute the test.

I built an AI-assisted E2E testing workflow around Playwright. A Jira or Notion ticket becomes the starting point. The system understands the requirement and codebase, uses a Playwright MCP server to explore the application, determines what state and test data are required, and identifies missing prerequisites.

If required data does not exist, the workflow guides the developer through creating the prerequisite data. Once the environment is ready, the system generates the Playwright test specification. Tests can then run daily or inside a CI/CD pipeline.

03

Bulk Resolution

Making large customer-facing operations feel like a normal product action.

100K rows average per API call

Customers needed to resolve or unresolve around 100,000 rows on average in a single API operation, directly from the product. The operation happens in front of the customer, so making the workflow feel like a hanging system was not acceptable.

The existing implementation had grown into a collection of filters and separate ticket-type implementations. The key architectural decision was to separate selection from execution.

Once filters have been evaluated and the ticket IDs are known, the IDs are materialized in Redis under a deterministic key representing the relevant account, user and filter combination.

The frontend receives that key. When the customer triggers the operation, the backend retrieves the materialized IDs and performs the resolve or unresolve operation without repeating the expensive selection work.

04

Restaurant Intelligence

Multi-platform analytics infrastructure built from scratch.

Multiple queries optimized to sub-100ms performance

Restaurant feedback lived across multiple platforms including Google, Yelp, Zomato and others. I designed and built the analytics infrastructure from scratch to provide unified insights across brands, locations and individual outlets.

The system handled hundreds of restaurants, thousands of outlets and millions of records per week. I worked across ingestion, processing, storage and the application layer rather than treating analytics as a reporting-only problem.

A major part of the work was database performance. I optimized multiple analytical queries through SQL changes, indexing strategy and query planning. Queries that previously took tens of seconds or around a minute were brought down to sub-100ms execution for key workloads.

The result was an analytics system where users could explore restaurant, brand and outlet-level insights without waiting on long-running queries.

02 / Approach

How I work.

I care about the entire path from a problem someone has to a system people can rely on. Architecture matters, but so do adoption, operations and what happens after launch.

01

Start with the real problem

Understand who is affected, what they are doing today and where the actual bottleneck is before designing the system.

02

Separate expensive work

Move computation to the right boundary. Materialize expensive work when appropriate instead of repeatedly making the user wait.

03

AI is part of the system

Models need context, tools, constraints, validation and clear execution boundaries to become dependable production software.

04

Measure what happens

Usage analytics, RUM sessions, system metrics and customer behavior tell you whether the thing you built actually works.

05

Own the whole path

Architecture, implementation, deployment, customer interaction, debugging and adoption are all part of shipping software.

06

Design for adoption

A technically correct system has limited value if people cannot understand it, trust it or fit it into how they already work.
